# السبب الجذري لانقطاع fetch failed المحلي

التصنيف: **ENVIRONMENT_RISK_OPEN**. الاختبارات الخضراء لا تلغي العَرض.

## ما رُصد

`@cloudflare/vite-plugin` يستدعي `Miniflare.dispatchFetch`. الفشل ليس استثناء JavaScript من Hono. `undici.fetch` نحو workerd يرمي `fetch failed` وسببه `Error: read ECONNRESET`. فيت يحول ذلك إلى صفحة HTML بعنوان Internal Server Error. طبقة الخطأ في التطبيق لا تصل إلى المتصفح في هذه الحالة، لذلك لا تظهر رسالة JSON المترجمة.

يظهر ذلك في كل تشغيل E2E تقريبًا على الطلبين المتوازيين في `e2e/setup.spec.ts`:

- `POST /api/v1/auth/bootstrap`
- `POST /api/auth/sign-up/email`

الاختبار يتوقع فائزًا واحدًا بـ 200 وخاسرًا بـ 409، وفيه إعادة محاولة واحدة محددة إذا عاد HTML فيه `fetch failed` على طلب لاحق بلا سر التهيئة. هذا التعافي قديم ومحدود، وليس إعادة محاولة عامة.

في اختبار قفل الفاتورة، نفس `ECONNRESET` أصاب `POST /api/v1/invoices/:id/corrections` على اتصال `page.request` المعاد استخدامه، بعد سلسلة طلبات نجحت. المعالج لم يسجّل دخوله، وقاعدة E2E بقيت عند الإصدار 2 بلا مراجعة. اتصال جديد عبر `browser.newContext({ storageState })` أكمل نفس الطلب وطبّق الدفعة. إغلاق المفتش عند `CI=1` (`inspectorPort: false`) أزال تحذير المنفذ 9229 ولم يوقف `ECONNRESET`.

منفذ 9229 يحمله workerd تابع لمشروع آخر على هذه الآلة. خادم التطوير على 43173 بقي كما هو. لم يُقتل أي منهما.

## ما لم يُفعل

- لم يُخفَ فشل JSON حقيقي (403/409/422).
- لم تُضف إعادة محاولات Playwright (`retries` تبقى 0).
- إخفاء طبقة Vite (`hmr: { overlay: false }`) يمنع اعتراض النقر فقط. الاتصال ما زال ينقطع.
- إنتاج التطبيق لا يعتمد على سياق متصفح جديد. ذلك التعافي خاص بمشغّل الاختبار المحلي.

## الأثر

طلب انقطع قبل تنفيذ المعالج لم يغيّر الفاتورة في الرصد. طلب انقطع بعد الالتزام ثم أُعيد إرساله قد يكرر الكتابة؛ لذلك لا تُعاد محاولات التعديل بشكل أعمى. اختبار القفل يستخدم اتصالًا جديدًا للتصحيح الأول ويسجّل السبب في `e2e/invoice-lock.spec.ts`.
